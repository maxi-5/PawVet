# Gestión del proyecto (Scrum)

Metodología: **Scrum** con sprints de una semana alineados con los hitos del curso (Hito 1, sección 3).

| Rol | Integrante | Desarrollo principal |
| --- | --- | --- |
| Product Owner y desarrollador | **Maximiliano Cuevas** | API Agenda y Atención |
| Scrum Master y desarrollador | **Vicente Bravo** | API Clínica e Identidad (base del Trabajo 2) |
| Cliente y validador | Docente (Enso Guidotti) | Valida el caso y revisa cada hito |

> Nota: en los documentos de los Hitos 1 y 2 los roles figuraban al revés (Vicente PO y Maximiliano SM). El equipo los ajustó a partir del Sprint 3: **Maximiliano Cuevas es Product Owner y Vicente Bravo es Scrum Master**. Las responsabilidades de desarrollo (qué API lleva cada uno) no cambiaron.

Ambos desarrollan el cliente React y las pruebas, revisan los pull requests del otro y tienen tareas asignadas en el tablero. La carga se reparte en partes iguales: cada uno es responsable de una API completa (código, contrato, modelo de datos y pruebas), de la mitad de las pantallas del cliente y de la mitad de la documentación (detalle en la sección 8.3 del informe).

| Sprint | Semana | Hito | Objetivo |
| --- | --- | --- | --- |
| Sprint 1 | Semana 2 | Hito 2 | Diseño: diagramas, contratos OpenAPI y estructura base de las dos APIs |
| Sprint 2 | Semana 3 | Hito 3 | Implementación: CRUD, JWT compartido, integración entre APIs y cliente React |
| Sprint 3 | Semana 4 | Hito 4 | Pruebas, documentación, informe y preparación de la defensa |

## Contenido

| Archivo | Qué es |
| --- | --- |

| `evidencia/` | Capturas del tablero y de los pull requests |

## Lo que solo puede completar el equipo

La rúbrica evalúa el proceso con evidencia real. Las secciones marcadas **Por completar** (fechas, revisión, retrospectiva, enlaces a PR y capturas) deben llenarse con lo que realmente ocurrió; el historial de Git (ramas, PR revisados y commits de ambos en distintas semanas) no se puede reconstruir después.
